# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.**
> 테스트를 먼저 쓴다. 예외를 만들고 싶다면, 그 충동 자체가 이 규칙이 필요한 이유다.

---

## 0. 프로젝트별 규칙 우선 (Precedence)

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 있으면 **그것을 우선**한다.
- **이 파일은 기본값(fallback)이다.** 프로젝트 지침이 없거나 침묵하는 부분에만 적용된다.

---

## 1. 적용 기준

### TDD를 반드시 적용

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API / 엔드포인트** (요청 처리, 응답 형태, 에러 코드)
- **유틸 / 순수 함수** (변환, 파싱, 검증)
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 쓴다)

### TDD가 불필요

- **타입 정의** (interface, type)
- **설정 파일** (config, env, 빌드 스크립트)
- **순수 UI** (마크업, 스타일링 — 로직 없는 프레젠테이션)
- **SQL / 스키마 / 마이그레이션**

경계가 모호하면 **적용하는 쪽**을 택한다.

---

## 2. RED-GREEN-REFACTOR 사이클

### RED — 실패하는 테스트를 먼저 쓴다

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 담지 마라.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 눈으로 읽고 넘어가지 마라.
- 실패 이유가 **"기능 미구현"**이어야 한다. 오타·import 누락·컴파일 에러로 인한 실패는 RED가 아니다.

### GREEN — 통과시키는 최소 코드만 쓴다

- 테스트를 통과시키는 **최소한의 코드**만 작성한다.
- **YAGNI:** 지금 테스트가 요구하지 않는 것은 만들지 마라. "나중에 필요할" 분기·설정·추상화 금지.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 실행해 확인한다.

### REFACTOR — 구조를 개선한다

- 중복 제거, 이름 개선, 헬퍼 추출.
- 리팩터링 중에도 **green을 유지**한다 (매 변경 후 테스트 실행).
- **새로운 동작을 추가하지 마라.** 새 동작은 다음 RED에서 다룬다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 사이클을 작게 유지한다.

---

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 스태시, 별도 파일 보관 전부 안 된다.
- 이미 쓴 코드가 아까운 건 sunk cost다. 테스트 없이 존재하는 프로덕션 코드는 부채다.

---

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순하면 테스트도 단순하다. 30초면 쓴다. 단순한 코드가 조용히 깨지는 게 가장 잡기 어렵다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 테스트 없는 코드는 리팩터링·검증이 불가능해져 그대로 굳는다. |
| "시간이 없다" | 디버깅에 쓸 시간을 앞당겨 쓰는 것뿐이다. TDD는 총 시간을 늘리지 않고 앞으로 옮긴다. |
| "삭제하면 낭비다" | 검증되지 않은 코드는 자산이 아니라 부채다. 유지하는 비용이 다시 쓰는 비용보다 크다. |
| "프로토타입이라 괜찮다" | 프로토타입은 살아남아 프로덕션이 된다. "임시" 코드일수록 테스트가 유일한 명세다. |

---

## 5. 성공 신호

- 커밋 히스토리에서 **테스트가 구현보다 먼저** 나타난다.
- 모든 프로덕션 코드 라인이 **실패했다가 통과한 테스트**로 거슬러 올라간다.
- 사이클이 작다: 한 번에 수십 줄이 아니라 한 동작씩 추가된다.
