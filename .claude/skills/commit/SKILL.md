# Commit

변경사항을 분석해 논리적 단위로 나누고, 저장소의 기존 컨벤션에 맞는 한국어 커밋 메시지를 작성한 뒤, 사용자 승인을 받아 커밋하는 스킬입니다.

핵심은 "한 커밋 = 하나의 이유"입니다. 나중에 `git log`나 `git bisect`로 이력을 훑어볼 사람(미래의 사용자 자신일 수도 있음)이, 커밋 하나만 보고 왜 그 변경이 있었는지 바로 이해할 수 있어야 합니다. 서로 다른 목적의 변경을 한 커밋에 뭉치면 이 목적이 깨지므로, 기본 동작은 **분리**입니다.

## 절차

### 1. 현재 상태와 컨벤션 파악

병렬로 확인합니다:
- `git status --short --branch` — 스테이징 여부와 현재 브랜치 확인. 브랜치가 예상과 다르거나(예: 의도치 않게 main), 이미 스테이징된 변경이 있다면 먼저 사용자에게 알립니다.
- `git diff` (unstaged), `git diff --staged` (staged) — 실제 변경 내용 확인.
- `git log --oneline -15` — 이 저장소가 실제로 쓰는 커밋 메시지 스타일을 확인합니다. 대부분의 저장소는 `<type>: <한국어 요약>` 형태(`feat: Google 모델 실패 시 자동 폴백 추가`처럼)를 쓰지만, 프로젝트마다 다를 수 있으니 로그에서 관찰한 실제 패턴을 따르세요. 로그가 비어있거나 스타일이 섞여 있으면 아래 기본 규칙을 씁니다.

기본 커밋 타입: `feat`(새 기능), `fix`(버그 수정), `refactor`(동작 변경 없는 구조 개선), `chore`(빌드/설정/의존성 등 잡무), `docs`(문서), `test`(테스트), `perf`(성능), `ci`(CI 설정).

### 2. 변경사항을 논리적 단위로 분류

`git diff`에 나온 파일과 hunk들을 목적별로 그룹핑합니다. 판단 기준:
- **같은 기능/버그를 향한 변경인가** — 예를 들어 새 컴포넌트 파일 추가와 그 컴포넌트를 라우터에 등록하는 변경은 한 그룹.
- **하나를 빼도 다른 하나가 말이 되는가** — 말이 된다면(독립적으로 존재 가능) 별도 그룹일 가능성이 높습니다.
- **설정/의존성 변경과 실제 코드 변경은 원칙적으로 분리** — `package.json` 의존성 추가와 그 의존성을 사용하는 기능 코드는, 의존성 추가가 그 기능만을 위한 것이 아니라면 나눕니다. 단, 새 기능을 위해 막 추가한 의존성이라면 같은 그룹으로 둡니다.
- **애매하면 사용자에게 물어보세요.** 자동 분류는 휴리스틱일 뿐이라, 그룹 경계가 불확실한 파일이 있으면 짐작해서 진행하지 말고 사용자에게 확인합니다.

파일 하나 안에 여러 목적의 hunk가 섞여 있다면(예: 버그 수정 한 줄 + 관련 없는 리팩토링), `git add -p`나 `git diff` 라인 범위를 활용해 hunk 단위로도 쪼갤 수 있습니다. 다만 실제로 섞여 있는 경우가 흔하지 않으니, 먼저 파일 단위 분류로 충분한지 확인하고 필요할 때만 hunk 단위로 내려가세요.

### 3. 스테이징 대상 결정 — 안전이 우선

- **절대 `git add -A`나 `git add .`를 쓰지 마세요.** 그룹별로 파일을 이름으로 명시해서 `git add <file1> <file2>`처럼 스테이징합니다. 의도치 않은 파일이 섞여 들어가는 걸 막기 위함입니다.
- 스테이징 전 `git status --short`로 어떤 untracked/modified 파일이 있는지 다시 확인하고, 다음에 해당하면 사용자에게 물어보기 전까지 스테이징하지 않습니다:
  - `.env`, `.env.*`, `*.pem`, `credentials*`, API 키/토큰이 들어있을 만한 파일
  - 프로젝트의 로컬 상태/캐시 디렉터리 (예: `.omc/`, `node_modules/`, `dist/`, `.cache/`) — 이미 `.gitignore`에 있다면 자동으로 제외되지만, 안 되어 있다면 커밋 대상에서 제외할지 사용자에게 확인
  - 이름만 봐도 이번 요청과 무관해 보이는 대량의 미확인 파일

### 4. 커밋 메시지 작성 (한국어)

각 그룹마다 형식은 `<type>: <한국어 요약>`. 요약은 무엇을 왜 바꿨는지 한 줄로, 명령형보다는 자연스러운 서술형("~추가", "~수정", "~변경")으로 씁니다. 파일 목록이나 diff를 그대로 나열하지 마세요 — 코드가 "무엇"을 보여주니, 메시지는 "왜/무엇을 위해"에 집중합니다. 필요하면 본문(빈 줄 다음 문단)에 배경을 짧게 덧붙일 수 있지만, 대부분은 제목 한 줄로 충분합니다.

### 5. 승인 요청 — 실행 전 반드시 한 번에 모아서 확인

`git commit`은 로컬 히스토리에 남는 되돌리기 번거로운 작업이므로, 실행 전 사용자 승인이 필수입니다. 그룹별로 나눈 뒤:

1. 제안하는 커밋 목록을 한 번에 보여줍니다. 각 항목마다 "포함 파일 → 커밋 메시지"를 명시합니다.
2. 사용자가 전체를 한 번에 승인/수정하도록 합니다(AskUserQuestion 사용 가능). 메시지 문구를 고치고 싶어하면 반영하고, 그룹을 합치거나 나누고 싶어하면 반영합니다.
3. 승인을 받기 전에는 어떤 `git add`나 `git commit`도 실행하지 않습니다.

### 6. 커밋 실행

승인된 각 그룹에 대해 순서대로:
1. `git add <해당 파일들>`
2. 커밋 메시지는 항상 heredoc으로 전달합니다(줄바꿈/특수문자 깨짐 방지):
   ```bash
   git commit -m "$(cat <<'EOF'
   <type>: <한국어 요약>
   EOF
   )"
   ```
3. pre-commit hook이 실패하면 `--no-verify`로 건너뛰지 말고 원인을 고친 뒤 다시 `git add` + 새 커밋을 시도합니다. hook 실패 전의 커밋은 발생하지 않았으므로 `--amend`를 쓰면 안 됩니다(직전의 다른 커밋을 덮어쓰게 됩니다).
4. 모든 그룹 커밋이 끝나면 `git log --oneline -n <그룹 수>`와 `git status --short`로 결과를 보여주고 마무리합니다.

## 하지 말아야 할 것

- `git commit --amend`, `git push --force`, `git reset --hard` 등 파괴적/이력 변경 작업은 사용자가 명시적으로 요청하지 않는 한 절대 사용하지 않습니다.
- 커밋 메시지에 Co-Authored-By 등 attribution을 넣으라는 별도 지시가 없다면 임의로 추가하지 않습니다(전역 설정에서 이미 비활성화되어 있을 수 있음).
- 승인 없이 커밋을 실행하지 않습니다. "커밋해줘"라는 요청 자체가 절차 전체(분석→분류→메시지 작성)에 대한 승인은 아닙니다 — 최종 실행 전 확인 단계는 항상 거칩니다.
